# QueenBee's - agent instructions

## Mandatory end-of-task planning rule

Every implementation prompt and completed implementation report must end with one recommended next step from docs/implementation-plan.md: name it, explain why, state prerequisites and owner approval, and give its acceptance condition. If blocked, recommend the prerequisite action instead. Do not execute the recommended next phase without explicit authorization. Avoid unrelated work and new features.

## Mandatory commit-and-push rule

**Every completed prompt or unit of work must end with a commit pushed to GitHub** before the report is written. This is not optional and not deferred to a later turn.

- Commit only the work of that prompt (plus its documentation and changelog entry). Never leave a completed change uncommitted or unpushed, and never batch several unrelated prompts into one commit.
- Run the checks that apply, then commit with a message that states the change and why.
- Push to `origin main` (`https://github.com/queenbeesbd/qb`) and confirm the remote-tracking branch is level with the commit. If the HTTPS remote cannot authenticate in the current shell, push the same commit over the SSH remote (`git@github.com:queenbeesbd/qb.git`) and fetch the tracking ref back over SSH - do not fall back to leaving it local.
- Never commit `.env*`, credentials, tokens, connection strings, dumps or generated secrets. `.gitignore` stays the guard.
- If a check fails and cannot be fixed within the prompt, do not push broken work silently: commit nothing, state the failure, and leave the tree clean.

## Scope and authority

- **The product is a single-store, owner-operated shop (ADR 0008).** QueenBee's is one store whose owner sells that store's own goods to that store's own customers. It is **not** a marketplace, multi-vendor platform, SaaS store builder or hosted platform for other businesses. There are no third-party merchants, vendor onboarding, seller registration, seller dashboards, commissions, marketplace payouts or tenant isolation - and no `store_id`, `tenant_id` or `merchant_id` abstraction. Do not add one "for future flexibility". Read `docs/decisions/0008-single-store-product-model.md` before any identity, role, authorization or multi-store work.
- **The admin overview is this shop's back office, not a SaaS dashboard.** It may use the reference's information architecture - greeting, KPI tiles, a revenue chart, an order-status ring, recent orders, honest worklists and quick actions - but it must never adopt the SaaS product around it: **no subscription, plan, renewal, upgrade, billing, trial, marketing banner or hero promotion**, no "visit website / copy link" promo card, and no capability the shop does not have (website visits/traffic, low stock, themes, app builder, phone app, vendor tools). A "quick action" links only to a real screen this owner can open; a panel states an actual stored fact, a derived count, or a stated gap. **Availability is a state, so an out-of-stock list is the replacement for "low stock"; there is no quantity to show.** Zatiq Easy remains a UX reference only.
- **Admin figures are labelled, not explained.** A dashboard or settings panel states a number with its label and, only where the number would otherwise mislead, **one short caveat** (for example "Excludes 2 orders without a recorded delivery split."). Never narrate the accounting rules, the derivation, an audit trail's completeness, a read timestamp or the implementation under a figure. Long explanatory essays read as a prototype, not a back office; move that reasoning to `docs/` and keep the screen on the task.
- **The site-open offer popup is one image and one switch (2026-11-06).** `offer_popup` is a singleton row; the owner uploads the image, writes its accessible description and toggles it. The square/16:9 frame is chosen from the uploaded file's own ratio by `saveOfferPopupUpload`; there is no shape selector and no image inventory path. The storefront opens it **once per browsing session**, keyed by the image and update time, as an accessible modal. Do not add scheduling, frequency capping beyond the session, exit-intent, countdowns, discount claims, links or tracking - the image is the whole offer.
- **"Merchant" is not a term for our own product.** Use **owner**, **store administrator**, **staff member**, **customer** or **payment provider**. The term is retained only where it is accurate: describing **Zatiq Easy** (genuinely a third-party multi-tenant merchant SaaS), the **payment counterparty** (this store's own bKash/Nagad account and statement), and catalog **provenance values** such as the image rights tag `merchant_source_pending_confirmation`. Do not mechanically find-and-replace it.
- **Four identity concepts stay distinct:** owner authority, optional staff permissions, customer identity, and anonymous public access.
- **Administration is owner-only at launch (D10, settled in ADR 0009).** Multiple owner accounts may exist and **every owner has full access**. There are **no staff or support roles** and **no general permission-management system** in the launch surface - the permission tables stay data rather than a code constant, but role management is not a launch feature. Any future staff role is a **new owner decision**, not an implementation convenience. The Phase 12 role-management screen is outside the approved launch surface and is a recorded follow-up.
- **Product availability is an owner-controlled `In Stock` / `Out of Stock` state (D19, ADR 0009)**, and an out-of-stock product **cannot be ordered**. Never present availability as a countdown, a restock date or an arrival promise. **Settled (ADR 0013):** availability is the **only** ordering gate - order creation writes **no** reservation, allocation, deduction or automatic availability change, separate valid submissions may create separate orders, and **overselling is accepted**. The quantity model, the movement ledger and the reservation stay in the schema (implemented and unused); do not remove them without a migration and explicit owner authorization.
- **A customer ban requires a confirmed fake order (D20, ADR 0009)** and is enforced server-side: sessions revoked, new orders refused inside the order transaction, checkout refused. A ban is **not** the review flag - the flag blocks nothing. A ban never cancels, refunds or deletes an order, and touches no payment, refund or reservation state.
- **Owner authentication is email and password (D22, ADR 0009).** **Resend email verification and Google sign-in remain deferred** for administrators: no verification step, no verification mail and no Google sign-in exists or should be added. A mail provider **is** authorized for **customer account security only** (ADR 0030). Owner credential recovery stays owner-issued and out of band.
- **Customer authentication is first-party (D17, ADR 0012).** Email and password with **scrypt** hashing, opaque 256-bit session tokens stored only as a **SHA-256 hash**, httpOnly `SameSite=Lax` cookies with idle and absolute expiry, account- and source-keyed throttling, customer-scoped CSRF, and **strict separation from owner/qbpanel credentials, sessions and permissions**. Email is the sole registration and sign-in identifier; **customer passwords are at least 8 characters with at least one letter or special character** (a digits-only password is refused), while owner/staff credentials keep the 12-character floor - `customerPasswordPolicyError` and `passwordPolicyError` are deliberately two functions; **recovery is the self-service link mailed through Resend (ADR 0030)** - the owner-issued one-time code was removed on 2026-11-08, and no code screen, code route or `customer.credential_reset` permission exists. Registration and sign-in have **no email-verification step and send no verification mail**. There is **no external identity, OAuth or SMS provider**. A **customer ban (D20)** revokes active sessions and refuses new orders inside the order transaction.
- **Customer/business activity records stay separate from internal administrative and security records (D23, ADR 0009).** One append-only store, distinguishable by construction: a denial carries `admin.action_denied` and a category, and a customer is never an audit actor type.
- **A refused action must be recorded durably.** A denial written inside the failing transaction is rolled back by the refusal itself - that was a real defect. Denials are written in their own transaction, never throw into the refusal path, are bounded per actor, and are not stored at all for an anonymous request. Do not move denial writes back into a caller's transaction.
- Read `README.md` and the relevant `docs/` file before changing code. Phase 0 produced the audit and plan; Phase 1 produced the working storefront. Phase 8 approved an **independent platform** direction - read `docs/decisions/0004-independent-platform-direction.md` and `docs/platform-architecture.md` before any backend work, and **`docs/data-model.md` before writing any schema, migration or state transition** - it is the designed source of truth for tables, constraints, indexes, state machines and transactions.
- Preserve user changes and `.pi/` (harness state, not application infrastructure).
- Ask before: replacing the framework, changing approved requirements, adding a major dependency, or anything irreversible. Reversible conventional choices are yours to make.
- Separate verified facts, assumptions, proposals and unresolved questions. Record significant approved choices in `docs/decisions/`.
- Keep documentation synchronized when an approved decision or requirement changes.

## Strategic direction (owner-approved, Phase 8)

- **QueenBee's is an independent e-commerce platform.** It owns its own backend, database, merchant dashboard, analytics and commerce workflows. Zatiq Easy is a **UX and feature reference only** - not a target backend, not a platform dependency.
- **No undocumented third-party APIs.** Do not build against Zatiq's private API (`easybill.zatiq.tech`), its internal endpoints, cookies or tenant identifiers. Do not treat any vendor's internal id as a QueenBee's identifier.
- **No real payment or production commerce operations** - no live charges, refunds, orders, courier bookings or customer communications - without explicit written authorization.
- **Ask before fundamentally changing approved architecture or business behaviour.** Stack choices (database, hosting, ORM, auth, payment, courier, image storage) require the owner's decision and a recorded ADR. Do not select one unilaterally, even as a conventional default.
- **Apply sensible conventional e-commerce logic** to reduce complexity - but never invent business policy. Delivery charges, refund rules, tax treatment and reservation timing are owner decisions, not engineering guesses.
- **Work in defined phases** (`docs/implementation-plan.md`) and verify at phase checkpoints rather than after every small task.
- **Preserve working behaviour and avoid unnecessary dependencies.** The existing storefront is the frontend foundation, not a prototype to discard.
- For UI/UX work use Design with Intent and Impeccable; use Superpowers brainstorming skills when comparing options.
- Apply Karpathy-style discipline: inspect first, make the minimal justified change, and verify actual behaviour rather than assuming it.

## Architecture constraints (accepted)

- **The schema and state machines are designed in `docs/data-model.md`, and the security model in `docs/security.md`.** Phase 10 produced the design; Phase 11 implemented the **database foundation** locally. Treat the design as the authority for table shape, state values and transaction behaviour, and treat "it is documented" as different from "it exists".
- **The database schema is implemented in `src/db/schema/` and migrated by `drizzle/`.** Drizzle ORM + drizzle-kit, pinned to stable `0.45.x` (ADR 0007). Never edit an applied migration - fix it with a new one. Never hand-edit a database to undo a migration. Run `npm run db:validate` after a schema change; `npm run db:check` catches an unregenerated or edited migration.
- **`src/db/client.ts` is the only place a database connection is created, and it is server-only.** Do not construct a driver, read `DATABASE_URL`, or import a driver package anywhere else. Do not import any `src/db/` or `src/server/` module from a client component: the environment module throws if it reaches a browser bundle, and `npm run check:secrets` verifies the built bundle.
- **Never store a secret in the repository, a fixture, a log or a `NEXT_PUBLIC_*` variable.** Configuration comes from the process environment per deployment target. `.env.example` holds placeholders only. Each environment (development, test, preview, production) must have its own endpoint and credential.
- **No QueenBee's-bound cloud resource exists, and none was created.** There is no Neon project, branch, database, role, credential or bucket for this product. The only Neon resource reachable from the account belongs to a **different product** and is **out of scope**: do not query or modify it. Neon PostgreSQL remains the approved _future_ provider direction (ADR 0005), and **provisioning it requires its own explicit owner authorization**. Provisioning, deployment and DNS changes each require separate explicit owner authorization - they are not implied by any approval to date.
- **Append-only is enforced twice, deliberately:** by revoked `UPDATE`/`DELETE` grants on `inventory_movement`, `order_event` and `audit_event`, and by a `BEFORE UPDATE OR DELETE` trigger that holds regardless of role. Do not remove either. `order_item` is frozen the same way.
- **Five separate state concepts must never be collapsed:** order fulfilment (`order.status`), prepaid payment (`order.payment_state`, retained but unused since ADR 0015), COD (`order.cod_state`), refund (`refund.state`) and the inventory reservation (`stock_reservation.state`, retained but unused per ADR 0013). A refund is not a stock fact; a delivered parcel is not collected cash; a verified payment is not consumed stock. Do not add a generic `status` column that means several of these.
- **Stock is enforced by the database, not only by code.** `inventory_balance` carries `CHECK (reserved <= on_hand)`, every reservation change goes through a guarded conditional update, and every movement is an append-only ledger row with a unique `movement_key`. Never decrement a counter directly, never read-then-write, and never add a second release path.
- **At most one active submitted payment claim exists per unit** - a **schema** constraint on a table the application no longer writes (ADR 0015). Do not relax it, and do not "restore" a claim write path without a new owner decision.
- **A submitted payment claim is never expired or released by a timer.** The claim write path is gone (ADR 0015), but the rule still binds anything that ever touches the retained table. Do not write expiry logic that can touch such a row.
- **Returned goods become sellable only after physical receipt and inspection.** No delivery event, refund, or cancellation restores sellable stock on its own.
- **Roles and permissions are database rows, not code constants.** D10 was open when the schema was designed and is now settled as **owner-only at launch (ADR 0009)**, but the model stays data: a hard-coded role list bakes a policy into the schema and makes changing it a migration. Do not hard-code a role list, and do not treat "owner-only at launch" as a reason to collapse the tables.
- **Deny by default, server-side.** Ownership comes from the session, never from a request parameter. Another customer's resource returns 404, not 403. Hiding a UI control is never the control.
- **The admin surface uses one control scale.** Two heights only - `--admin-control` (40px) for buttons, inputs, selects, filter tabs and icon buttons, `--admin-control-sm` (34px) for dense-row secondary controls - with the small variant growing to 40px below 720px. A destructive trigger is never smaller than the action beside it, it ends on the same edge as the primary action it accompanies (never at the top of the row beside a field), controls sharing a row share a height, and a required field must never be labelled optional or hidden behind a collapsed disclosure. **A list filter is the one allowed exception to that disclosure rule, and only in this shape:** above 720px a segmented row, at and below 720px a 40px disclosure whose **closed summary names the filter in force**, opening into 40px rows with counts. It is not a licence to collapse options that are not filters. The phone rail was removed because it hid four of eight order statuses behind an unmarked swipe (owner feedback: hard to use) - do not reintroduce a horizontally scrolling filter, and do not replace this with a `<select>` that needs JavaScript to navigate. `npm run verify:admin` sweeps the rendered heights and fails on a third value.
- **Administration is owner-only and has no role-management surface.** Every owner account has full access; there is no staff or support role, no role picker, no permission matrix, and no permission-management UI (D10, ADR 0009). The Phase 12 staff and role screen and its four API routes were **removed in Phase 13** - do not reintroduce them, and do not add a second account-provisioning channel. The only non-session way to create an account is the host-shell `npm run staff:bootstrap` CLI, which is not reachable over HTTP.
- **The panel lives at `/qbpanel`, and nothing may index it (ADR 0031, 2026-11-09).** The administrative tree is `/qbpanel/...` and its mutations `/api/qbpanel/...`; `/admin` and `/api/admin` are **not** aliased and answer 404. `ADMIN_ROOT`, `LOGIN_PATH`, `REDEEM_PATH`, `ADMIN_PATH_PATTERN` and every navigation constant come from `src/server/auth/constants.ts` - never write one of those paths as a literal. `next.config.ts` sets `X-Robots-Tag: noindex, nofollow, noarchive, nosnippet` on both trees and `src/app/robots.ts` answers `Disallow: /`; **never name the panel path in `robots.txt`** - a `Disallow` line publishes it. The path is not a security control: this repository is public, so authorization stays server-side and per-permission, exactly as before.
- **An owner session is long-lived but still ends (ADR 0031).** `SESSION_ABSOLUTE_MS` is a year and `SESSION_IDLE_MS` 30 days, clamped so idle never passes the ceiling. Do not shorten them back to the Phase 12 hours "for safety" - the owner runs this shop alone and being signed out on every open was the reported failure. Sign-out, a password change and owner revocation still revoke immediately; never add a way to survive those.
- **The Android app is a shell, not a second application (`android-app/`).** A Capacitor project whose WebView loads `<deployment>/qbpanel`; it holds no business logic, credential, API token or copy of the store, and there is no offline panel. It is **`android-app/`, never `app/`**: Next.js resolves a root-level `app/` directory as its own route directory ahead of `src/app/`, which silently replaces the whole application with an empty tree. Icons and splashes come from the owner's `logo.jpeg` via `android-app/scripts/build-icons.mjs`; the debug APK is committed at `android-app/dist/`, and a release build needs the owner's own keystore, which is gitignored.
- **Availability is a state, never a quantity.** `product.availability` holds exactly `in_stock` or `out_of_stock`, defaults to `out_of_stock`, and is the only gate the authoritative server-side orderability check reads (D19, ADR 0010). Do not derive it from stock, do not add a third state, and never let a client supply it. **No inventory movement, deduction or reservation is written, and therefore overselling is not prevented** - settled in **ADR 0013**: that is **accepted** and managed operationally, and no reservation behaviour may be added without a new owner decision.
- **A product create/edit screen is its own route, not a query parameter on the list** (Phase 35). `/qbpanel/catalog/new` and `/qbpanel/catalog/[productId]`; `?new=1` and `?edit=` were removed rather than kept as aliases. A filtered, paginated list and a full-height editor are different tasks, and sharing a URL let a refresh lose whichever one the owner was in. Follow the editor pattern in `docs/design-system.md`: one action bar (sticky, never a second one at the bottom), a required summary that names the empty fields, a preview that shows only what was typed, and explicit validation that states the missing set rather than relying on native bubbles. The same rule covers the promo editor (Phase 38) and the category editor (Phase 36), and each editor's write route takes a `returnTo` **allowlisted by exact shape** (never an open redirect) and **returns a refusal to the editor that produced it**, so a create editor must render notices too.
- **Two category defects fixed in Phase 36; do not reintroduce either.** A slug stays **taken after archiving** (the unique index holds it), so the clash check covers **every** row - filtering to live rows let the clash reach the database as a **500** instead of a conflict notice. And an **unticked checkbox posts nothing**, which the service reads as `isVisible: true`, so the editor posts an explicit `false` in a hidden input beside the box (box at `value="true"`). Any new boolean field needs the same pair.
- **Category and brand editors are full pages with one shared image field.** `/qbpanel/categories/new|[categoryId]` and `/qbpanel/catalog/brands/new|[brandId]` use the same sticky action bar and `CatalogImageField`: a local upload prepared in the browser, a preview, an optional inventory choice, and removal as an explicit checkbox. The image saves **with** the record in one transaction; there is no "create first, then attach" step. Brand creation is its own route, not a disclosure under the product list; the old image-only routes (`/api/qbpanel/catalog/category-image`, `/api/qbpanel/catalog/brand-image`) were removed rather than kept as a second path.
- **Subcategories are one level deep (Phase 31, owner-authorized 2026-11-06).** A category editor offers a parent picker whose options are **live top-level categories only**, so a child can never become a parent and a third level cannot be created. A category that already has live children is **locked to the top level** (the form states why instead of offering a picker), and the service re-enforces the same rule. `parent_id` is still read to *count* subcategories, because archive is refused while a live child exists; archiving a child then its parent is the supported order. The storefront shows only root categories on the index, homepage rail and navigation; a parent page lists its children and includes their products, and a child page's breadcrumb names its parent.
- **Circles are the shop's one frame for a discovery image (2026-11-05).** `BrandCircleRail` draws one round tile per brand in the shared `Carousel` (`size="circle"`), the logo **filling** the circle with a centre crop (`object-fit: cover`) exactly as a category photograph does, with a **shared letter-mark** fallback (`src/components/LetterMark.tsx`) in the same circle: the first letter in the display face on a pale plate chosen by the letter, so every A looks like the same alphabet (owner direction, 2026-11-05); the square-card `BrandCarousel` was removed rather than kept beside it. **The category index and the brand index draw the same circle** (owner direction), and a category's photograph **fills** its circle with a centre crop (`object-fit: cover`) rather than sitting inside a square. The header's brand mark is the same shape: the owner's own `logo.jpeg`, generated into `public/brand/logo-round-{96,192}.jpeg` by `npm run assets:brand` and drawn inside a 44-48px circle with `cover`, so any square upload is centre-cropped to the circle. The brand's mark is `brand.logo_key`, set in the brand editor (`/qbpanel/catalog/brands/new`, `/qbpanel/catalog/brands/[brandId]`) by a local upload or from the server's own asset inventory (`POST /api/qbpanel/catalog/brand`, `catalog.write`, audited). There **is** a browser upload for a category photograph, a brand logo, a product photograph and a hero banner (2026-11-05): `src/server/catalog/uploads.ts` is the only module that touches an uploaded file, it decodes with `sharp` under a 40 MP ceiling, applies EXIF orientation and **re-encodes to WebP only** at **320 / 600 / 1050** (product and squares) or 800 / 1600 (hero), and the key, dimensions, content type and byte size all come from the decoded bytes, never the request. The 320 thumbnail is what a 116px circle downloads; a card never fetches the 1050 master. The file input (`AdminImageInput`) first **downscales and re-encodes in the browser** (long edge 1600px, WebP), so a 5-15 MB phone JPEG fits under the 4 MB request cap; HEIC that the browser cannot decode falls back to the server's refusal. Bytes go to `public/catalog` when writable and to the object-storage bucket when `CATALOG_STORAGE_*` is set, and that credential **must carry `storage:write`** - a read-only scoped key answers 403. `npm run assets:optimize` re-encodes the whole stored tree to this rule; `npm run assets:logos` trims each brand logo's empty border and rebuilds its square variants so the mark fills the circle instead of floating inside it. JPEGs generated before these rules remain dead bytes and are not referenced.
- **`product.short_description` is one English line, not a second description.** It renders under the price on the product page and is omitted entirely when null. There is deliberately no SEO description and no rich text: an unrendered column is a promise nobody keeps, and untrusted HTML is never rendered.
- **Product imagery has two sources: an upload, or the server's own asset inventory.** Since 2026-11-05 the owner can upload a photograph from their computer for products, categories, brand logos and hero banners (`src/server/catalog/uploads.ts`). The upload is decoded with `sharp` (40 MP ceiling, EXIF rotated, re-encoded, metadata stripped) and the key, dimensions, content type and byte size are produced from the bytes - never from the request, never from the extension. An association with an existing asset is still validated by format **and** against the inventory derived from `public/catalog`. Never accept a client-supplied path, URL or image metadata, and never let a file be stored only in Vercel's ephemeral filesystem: an upload writes to `public/catalog` when writable **and** to object storage when configured, refusing when neither is available.
- **Catalog deletion refuses rather than cascades.** A product referenced by an order is not archived; a category referenced by a live product or subcategory is not archived. Prefer an explicit refusal the owner can act on over broken references or cascading loss.
- **A price arrives only as the owner typed it.** `parsePoisha` accepts a decimal BDT string and returns integer poisha; it **refuses a bare number**, because a number has no unit and guessing wrong is a 100x money error. Never parse a price with `parseFloat`, and never accept a formatted price, a total or a discount from the browser.

- Next.js App Router + strict TypeScript, npm with committed lockfile. See `docs/decisions/0001-nextjs-typescript-foundation.md`.
- Server Components by default; add `'use client'` only where interaction requires it.
- Styling is CSS Modules plus CSS custom-property tokens in `src/app/globals.css`. Use tokens, not raw hex values, in components.
- **All money is integer poisha** (`1 BDT = 100`). Never use floating-point arithmetic for money, and never store a derived discount - derive it.
- Global client state is limited to **one** external store (`src/features/cart/cart-store.ts`) consumed with `useSyncExternalStore`; the locale store was removed with the second language (Phase 28). Do not add a state-management library. Do not call `setState` synchronously inside an effect; the lint rules reject it.
- **The cart provider holds lines and counts, never product records** (2026-10-29). The storefront layout passes the catalogue's **ids** to `CartProvider`, so a restored line is still validated against what the shop sells and the header badge counts stored quantities without a product lookup. The two routes that draw lines, `/cart` and `/checkout`, receive the compact projection (`src/features/cart/cart-product.ts`) from their own server pages and resolve prices with `resolveCartLines` (`cart-lines.ts`). Do not put the whole catalogue back in the layout provider: that is what made every route carry 1,477 products.
- **A cart line's ids are mirrored into a first-party cookie, and nothing else is** (2026-10-29).
  `qb_cart` holds ids only (`src/features/cart/cart-cookie.ts`), `path=/`, `SameSite=Lax`, 30 days, removed
  rather than emptied when the cart is empty. `/cart` and `/checkout` read it and project **only those
  products** (`selectCartProducts`), which is what keeps those two routes at ~9 KB gzipped instead of 81.
  Never put a quantity, price, name or total in it: the value is untrusted and may only select which
  products a page mentions. When a page cannot draw a stored line, `useCartProjection` refreshes once and
  then says so, and `/checkout` refuses to submit - an order must never be placed with a line silently
  missing. Do not pass the catalogue to those pages again, and do not widen this cookie into a second cart.
- **Font weights are restricted to 400 / 500 / 600 / 700.** Inter is variable (100-900) but Noto Sans Bengali only ships those four, so any other value renders at different effective weights in the two scripts. Do not introduce 550/650 or intermediate values.
- **Never apply letter-spacing to Bengali text.** Negative tracking distorts conjunct clusters. `html[lang='bn']` resets it for headings; keep it that way.
- **Phone navigation is a three-zone bar plus the tab bar (owner direction, 2026-11-05, superseding the 2026-10-23 "no drawer" ruling).** Below 1024px the header is **menu control on the left, logo centred, cart on the right**, with the search row beneath it, and the fixed bottom tab bar (`src/components/StorefrontTabBar.tsx`) stays the primary navigation (Home / Shop / Categories / Brands / Cart / Account). The menu opens a **modal drawer** listing home, the catalog, the category index, every department, brands, cart and the account page: focus moves into it, Tab is trapped, Escape closes it, the page behind is locked and focus returns to the trigger; it closes on navigation and above 1024px. From 1024px the desktop header draws the same circular mark and a **six-destination row in one fixed order - Home, All products, Categories, Brands, Offers, New In** - then the search, account and cart controls; neither the drawer nor the tab bar is rendered. The inline department shortcuts are gone from that row (departments live in the drawer, the Categories index and the filter rail), and a destination that carries a query (Offers, New In) never claims `aria-current`. **The tab bar is `--brand-primary` light lavender (`#c8b6ff`) with `--color-ink` labels (9.3:1). The current destination is a **deep-lavender capsule** (`--brand-primary-deep`) behind the icon with a white glyph (`padding` + equal negative `margin` on `.icon`, 40x30, so the tab's layout never sees it) plus a 700 label; the white capsule was removed on owner feedback - it read as a hole in the bar; the cart count is pink with ink on it. Never put white text or a white glyph on the lavender (1.81:1), never fade the labels to soften the colour, and never fill the whole tab cell with the active state - a near-square block under a label reads as a bubble, not a tab.** Do not turn the drawer into a second copy of the tabs' destinations, and do not hide category filtering or the category routes.
- **The homepage hero advances by itself every 9 seconds and loops** (owner direction, 2026-11-05): after the last banner the first returns, and the arrows wrap instead of disabling. Hover and keyboard focus pause it, and `prefers-reduced-motion` stops it entirely. There is no play/pause control - the owner asked for a sliding carousel, not a media player. 

**The phone landing is short, and the hero is not a second one (owner direction revised by the 2026-11-02 redesign and Phase 51).** The hero is the **owner's image carousel** at every width - one 16:9 banner, swipeable on a phone, with the category rail and the first product row still on the first screen. Do not reintroduce the removed copy-and-three-photographs composition or a phone-only spotlight row, and do not hide the carousel below 720px. `#categories` stays in the DOM: the fixed tab bar and the header reach the category index, and `verify:browser` check 36 asserts the phone carousel, the rail and the first product, while check 36d asserts the desktop arrows and rail.
- **The homepage hero has no tinted band.** The carousel sits on the page canvas like every section below it: one surface, not a sequence of coloured blocks. A pastel strip behind the first screen read as a promotion rather than as the shop itself, so it was removed (2026-10-23) - do not reintroduce a background colour, a gradient or a border under the hero.
- All catalog imagery renders through `src/components/ProductPhoto.tsx`. Never emit a raw `<img>` for a product or hardcode an image path - paths are derived from the image `key` in `src/lib/images.ts`.
- **Curated selections are id lists, never a flag on the product record.** The featured row and the "more to explore" collection are declared as product-id arrays in `src/data/curation.ts` and seeded into the database's `collection` / `collection_item` tables (ordered by `position`) - the storefront reads them from there (Phase 14, ADR 0011). Do not reintroduce a `featured` boolean on `Product`, and do not exceed the declared caps (featured 5, collection 5) - `npm run check:catalog` asserts the fixture lists (which are the seed) resolve, do not repeat, do not overlap, and stay within cap. Both selections are rendered on the homepage since 2026-10-23.
- **Recency is a real stored fact, and only a real stored fact (D6, Phase 26).** Every homepage product row uses the one standard full-width grid. The homepage "Recently added" section shows products ordered by `product.created_at` descending, with `product.id` descending as the deterministic tie-breaker. The timestamp is the database's own `created_at` column - never `published_at`, an id ordering, a list position or a fixture constant. Do **not** re-derive the order in a view, do **not** pad a row with a repeated or invented card, and if a source cannot state when a product was added (the fixture has no capture dates, so `createdAt` is `null`) the section shows fewer products or is omitted. **The homepage hero is not a recency surface (Phase 51):** it is the owner's ordered image carousel, it makes no arrival claim, and the removed `selectHeroProducts` selection must not come back. **Never present curated products as recency, popularity or sales:** the featured row and the "more to explore" collection are owner curation and must never be worded as arrival order.
- **Homepage order is hero, Shop By Category, Shop By Brand, On Offer, Most Selling, Recently Added, More To Explore (owner decision, 2026-11-05), and every section heading is centred and title-cased with at most one route into its full listing beneath it. The homepage never shows an out-of-stock product (owner direction, 2026-11-05): `selectHomepage` filters the catalogue to `availability === 'in_stock'` once, before every row is selected, because availability is the only ordering gate and a shelf of dead ends is not a shelf. The empty state still describes the catalogue rather than the filtered list. The featured row was **removed** by that order; its curation (`FEATURED_PRODUCT_IDS`) still seeds, so restoring the row is a view change, not a data migration. **Most Selling is a derived fact, never a curation:** it ranks products by real `order_item` units, excludes cancelled orders, yields to Recently Added (recency cannot be filtered without becoming a false claim), and is **omitted entirely when the shop has sold nothing** (owner direction, 2026-11-07) - a heading over an empty shelf is a promise the shop cannot keep. Homepage product cards carry their own **Add to cart** control (disabled, and labelled, when unavailable). The three fixed sections publish five products each - the full-width grid is two columns on a phone, three from 720px and five from 1200px - so five completes the desktop row exactly and the two-column phone grid lets the last card span. There is deliberately **no four-column step**: five cards in a four-column grid strand one, and a fifth card at 1024px would be ~175px, under the 200px floor. Below 1200px a five-card section reads 3 + 2. Do not "fix" an odd count by shrinking the grid: `ProductGrid` measures its own child count and lets a lone last card span the phone row.
- **"More to explore" is a browse row, not a selection (2026-10-23).** It leads with the curated collection and then continues into every product the rows above did not show, up to **ten** (two desktop rows), and it is the only section with a button - a centred "View more products" link to `/products`. It is the one place a short catalog legitimately shows a partial final row; never pad it with a repeat to fill the row. The featured row and the offer row are each exactly one row.
- **The comparison price is struck through only when it is genuinely greater than the current price.** Gate it on the derived saving being non-null; never print a discount that `discountAmount`/`discountPercent` did not compute.
- **Every product card on a shoppable surface carries Add to cart (owner direction, 2026-11-05).** The homepage rows and the `/products` / category listing both pass `addToCart`; only the related-products row on a product page omits it, because that page's own buy action is already on screen. The control keeps its three honest states (in stock adds, out of stock and unknown are disabled and labelled).
- **There is no horizontally scrolling product row.** The featured shelf was removed on 2026-10-23: it existed to reach a sixth card that did not fit, so it is now a static row of five with no controls or scroll bar. If a horizontal row is ever reintroduced, nested grid items need `min-width: 0`, `overflow-x: auto` alone is not enough - it also needs `contain: layout paint` - and it must derive its card width from `ProductGrid`'s breakpoints (2 columns below 720px, 3 from 720px, 5 from 1200px). See `docs/design-system.md`.
- **The catalog listing is one view over one server-derived snapshot** (`CatalogView` plus
  `src/features/catalog/listing/`). `/products` and `/categories/[slug]` share it. Category is a route,
  never a checkbox; brands are repeated `brand` parameters; price is `min`/`max` in whole taka (poisha
  in the query); availability is repeated `availability`; `sort` and `page` live in the URL. Facet
  counts, price bounds and the brand list are derived server-side from the same snapshot the grid
  renders - never hard-coded, never fixture-only. Every filter change resets `page` and pushes without
  scrolling; the rail, chips, drawer and URL are one state. The desktop rail is **static and never
  scrolls inside itself** - the page is the only scroll container. Category is open; Brand, Price and
  Availability start collapsed and state their active value in their own header, and an applied facet
  opens its section on load. Do not make the rail sticky with its own `max-height`/overflow, and do not
  hide a collapsed section's applied state. Below 1024px the rail is a modal drawer with a draft,
  Apply/Reset, focus return and body lock, and the shell's global search is hidden on listing routes so
  the collection search is the only one. **The desktop filter rail is sticky** (`position: sticky`,
  capped to the viewport, scrolling only when the expanded rail is taller than the screen - owner
  direction, 2026-11-05), so the filters travel with the grid; its secondary sections still start
  collapsed. **One card frame everywhere: `CARD_FRAME` and
  `LISTING_CARD_FRAME` are both 4:5** (owner direction, 2026-11-05 - the 5:4 homepage crop cut the
  product away and made a homepage card differ from the same product's listing card). Do not reintroduce a
  second card frame, and do not replace the checkbox rows with pills, invent a facet the
  catalog cannot back, or let a count disagree with the grid. See `docs/design-system.md`.
- **The storefront catalog snapshot is cached across production requests (2026-11-07).** `getStorefrontCatalog` reads through `unstable_cache` under the tag `storefront-catalog`, with a five-minute TTL as a backstop. Every catalog write route (`product`, `category`, `brand`, `availability`, `image`) calls `invalidateStorefrontCatalog()` **after** its transaction commits, so an owner's change is visible on the next request. Development and the test runner read directly because `unstable_cache` needs Next's incremental cache. Do not reintroduce a per-request full-catalog read, and do not add a catalog write path that skips the invalidation. Catalog images are proxied by `/catalog/[...path]` with immutable browser/CDN headers so repeat views are served by Vercel's edge instead of Neon; do not restore the direct bucket redirect.
- **Catalog data is reached only through the typed accessor contract, which is now backed by the database** (`src/server/catalog/storefront.ts`, Phase 14, ADR 0011). This is the load-bearing seam: view components depend on the accessor contract and the `Product` shape, never on SQL or a server-only module, so the source behind it can change without touching a view. Keep it that way. `src/data/` survives in **two roles only** - the deterministic local/test seed (`npm run db:seed:catalog`) and an explicit **development-only** opt-in (`QUEENBEES_STOREFRONT_FIXTURE=1`, off by default, refused outside development). It is **never a fallback**: a database read failure surfaces through the error boundary instead of substituting fixture rows.
- Do not add a database, ORM, auth provider, CMS, UI component library, animation library or test framework without a demonstrated need and approval. This applies with extra force now that a backend is planned: **stack selection is an owner decision recorded in `docs/platform-architecture.md`**, not an incidental choice made while implementing a feature.
- **The storefront never writes authoritative commerce state.** The cart stores ids and quantities only, never prices. Prices, discounts, stock and totals are recomputed server-side.
- **Analytics are derived from QueenBee's own database**, not from a third-party analytics product, so revenue figures reconcile against orders and customer data is not shipped to a vendor. See `docs/qbpanel-dashboard.md`.
- **Money and workload are bucketed by different clocks, and never mixed.** Revenue, items sold, customers served, discounts and courier costs are grouped by `completed_at` (the moment payment was recorded); orders placed and the status mix by `placed_at`. The interface labels which is which. Day buckets are cut in **`Asia/Dhaka`** in SQL, because "today" for this shop means Dhaka's today - do not bucket in the database session's timezone.
- **Traffic figures come from the shop's own first-party visit log, and only from it (ADR 0027, owner-approved 2026-11-07).** `visit_session` and `visit_event` are written by `POST /api/track` from a small storefront beacon: a random session id in an `HttpOnly` `qb_visit` cookie, the path **without its query string**, a coarse device class and the step. **No IP address, no user-agent string, no fingerprint, no referrer, no cross-site identifier and no third-party script** - do not add one, and do not add a vendor analytics product. A session is **never linked to a customer or an order**: `placed_order` is a boolean, not a foreign key. Crawlers and link previews are not recorded. Every figure names what it counts - a **visit is a session, not a person**, **live now** is a request in the last five minutes, and **carts left behind** is a cart with no order, never a "lost sale". **A visit row is kept for 90 days and then deleted** (owner decision, 2026-11-07): the sweep runs in `POST /api/track` after the response, at most once an hour per instance, and `npm run visits:prune` is the explicit run. The window is the longest period the screen offers, so a figure can never read a row the sweep would have removed. Never print an estimate where nothing was measured.
- **Traffic is its own screen, and a reader's division is derived, never asked (ADR 0033, 2026-11-09).** `/qbpanel/traffic` holds the shop's own visit log; `/qbpanel/analytics` keeps the money and no longer carries a traffic block, because a visit is not an order and the two are never added together. Both sit under Overview behind `order.read` (owner-only, D10). The screen states sessions **today / 7 days / 30 days / all time** (all time is the **retained** 90-day log, and it says so), live now, carts left behind, visits per day, the device split, the funnel and the most-read paths. **The area is one of the eight divisions or `outside_bd` or null**: `divisionFromHeaders` maps `x-vercel-ip-country` + `x-vercel-ip-country-region` (ISO 3166-2:BD is exactly the divisions) and nothing else is read or stored - no address, city, coordinate or fingerprint, and **never** `navigator.geolocation` or a location prompt in the storefront. A missing or unknown header is `null` ("not known"), never a default; the row is filled once and `coalesce`d afterwards. Do not widen the bucket, do not store the input, and do not add a per-visitor identity.
- **A 404 is a shop page, not an apology (2026-11-09).** Both 404s - the root one for an unmatched URL and the storefront one raised by `notFound()` - render `NotFoundView`: the real in-stock shelf as a specimen mosaic, the same products as a menu with their real price and pack, the category index and a search. `loadNotFoundShelf` reads the same cached catalogue snapshot every storefront page uses and **never throws**: a failed read renders the page without a shelf and states the gap. It shows only `availability = 'in_stock'` products, invents no reviews, arrivals, counts or "popular" claims, and its shelf **links** rather than adding to the cart (the root 404 has no cart provider at all). Keep the direction: specimen-catalogue tiles on flat fields, no cards, no icons.
- **Charts are hand-drawn SVG in `src/app/(admin)/qbpanel/_ui/charts.tsx`, and no chart library may be added** (ADR 0021 D5). The plot scales, the stroke stays 2px (`vector-effect="non-scaling-stroke"`), axis text is HTML beside the plot rather than scaled SVG text, and every figure also emits a screen-reader table. A window with no data draws a sentence, not four zero ticks.
- **A promotion code is a rule plus a derived use count (ADR 0021).** `promo_code` holds the rule; `promo_code_redemption` holds one row per order (unique per order, append-only by trigger). Usage is `count(*)`, **never a counter**, and `max_redemptions` is enforced by counting inside the order transaction with the code row locked. `order.discount_minor` is an **immutable snapshot** covered by the order immutability trigger, and the schema checks `total = items_subtotal - discount + shipping`. Never recompute an order's discount from the live code - an owner editing a code must not rewrite what a customer was charged.
- **One code per order, no stacking, no automatic campaign, no timer.** `starts_at`/`ends_at` are evaluated at use; nothing publishes, expires or sweeps a code on a schedule. Switching a code off is the owner's explicit action and leaves existing orders untouched. There is no delete path: a mistake is paused.
- **A code that cannot apply refuses the order rather than charging more than the screen stated.** The checkout preview and order creation share one evaluator (`src/lib/promo.ts`) and one line pricer (`resolveOrderLines`); the preview writes nothing and requires a customer session and CSRF. Never accept a discount amount from the browser.
- **Promotion CRUD is gated on `settings.write`** (a code sets what a customer is asked to pay), and the analytics screen on `order.read` (it is another view of order rows). Audit `promo.created` / `promo.updated` / `promo.activated` / `promo.deactivated`; a redemption is **not** audited, because the order and its event log are the record.

## Design principles

- Minimal, premium, product-led. Light lavender `#C8B6FF` (owner choice, 2026-11-05) and pink `#F6B3CC` are anchors used deliberately. Storefront filled controls use the lavender field with ink (`--color-button` / `--color-button-ink`, 9.3:1); white on it is 1.81:1 and is never used. Admin primary buttons use the same field; admin danger buttons keep their red, and navigation/active states keep `--color-action`.
- No decorative clutter, gratuitous gradients, excessive rounding, pill-shaped controls by default, arbitrary animation, or generic pink beauty-store styling.
- Desktop and mobile share routes, data and business logic. Mobile may adapt presentation, never behaviour.
- **Two pieces of floating phone chrome, both server-driven and both filled with the brand (owner direction, 2026-11-05).** A **cart box** sits at the right edge, **vertically centred** (owner direction, 2026-11-05) and is **not** drawn on `/cart` or `/checkout`, which already state its two facts: it states the item count and, when every line can be priced, the subtotal — the count comes from the stored lines, the unit prices from `GET /api/cart/prices`, and the subtotal is display-only because checkout recomputes every line. A **support rail** sits in the **bottom-right corner**, above the tab bar on a phone, with a Facebook and a WhatsApp button, whose addresses are the owner's `store_setting` values (`support.facebook_url`, `support.whatsapp_url`, Settings → Support links); a link that is not set renders no button, both open in a new tab with `rel="noopener noreferrer"`, and both are validated as absolute `https` URLs at save time. The marks are ours, drawn white on the brand fill — never the providers' brand colours. **Both surfaces use the owner's light lavender `--color-button` (#c8b6ff) with ink marks: 9.3:1. White on it is 1.81:1 and is never used for a glyph or a label**, which is why the field only ever carries ink.
- **A phone never zooms the page** (owner decision, 2026-10-29). The viewport is `maximum-scale=1, user-scalable=no`, `html` carries `touch-action: manipulation` and `text-size-adjust: 100%`, and every form control is at least 16px below 720px - iOS magnifies the page when a control under 16px is focused. This trades pinch-zoom away deliberately; the reasoning and the cost are recorded in `docs/design-system.md`. Do not re-enable zoom, and do not shrink a control below 16px on a phone.
- **One control size for a form** is `--text-control` (15px desktop, 16px phone). On a phone `--admin-control-sm` is 40px, not 34px; a 34px control must never sit beside a 40px one.
- Reference Ghorer Bazar for functional patterns only. Never copy its identity, content, assets or grocery taxonomy, and do not inherit the previous QueenBee's visual design.
- Typography must be verified for Bangla: no letter-spacing on Bengali text, longer base line-height, and no fixed-height text containers.

## Honesty rules (non-negotiable)

- Never invent stock, arrival dates, reviews, ratings, sales counts, authenticity guarantees, ingredient claims, discounts, delivery promises or testimonials.
- When verified data does not exist, state the gap in the interface. The homepage and product pages already do this for dates and descriptions - keep that pattern.
- **The storefront is no longer presented as a demonstration (owner decision, 2026-10-23, ADR 0020).** The locked demo notice and the footer's demonstration sentence were removed, and `npm run check:catalog` / `npm run verify:browser` now assert that **no** demo or preview wording remains. Do not reintroduce a demo notice, a preview badge or a "no payments are taken" line. Every other honesty rule still binds: no invented stock, dates, discounts or delivery promises, and no capability the product does not have.

## Security and data

- The frontend is **never** authoritative for prices, discounts, stock, permissions, totals, payment status or orders. Production validation belongs to a trusted server.
- Never put secrets in client bundles, `NEXT_PUBLIC_*` variables, documentation, logs or committed files.
- No merchant backend access, live security testing, order submission or customer-data collection without explicit written authorisation and a defined scope.
- **The Phase 7 backend audit is complete; its authorization is spent.** Do not log into `merchant.zatiqeasy.com` again, and do not re-run backend reconnaissance, without fresh written authorization for a specific question. The audit's findings are in `docs/backend-capability-audit.md`.
- **The platform's private API (`easybill.zatiq.tech`) is not a supported integration surface.** Do not build against it. A supported interface must be confirmed by the provider first.
- Merchant-tenant credentials must never reach the browser, the storefront bundle, `NEXT_PUBLIC_*`, logs, docs or committed files. Any future integration keeps them server-side only, in a least-privilege identity.
- **No customer-submitted artefact is ever proof of payment.** A screenshot, sender number, transaction reference or confirmation message is not evidence, and the COD release collects none of them. If a gateway is ever approved, only a server-verified provider response may mark anything paid.
- **Never request, collect, log or store payment PINs, OTPs, passwords or mobile financial service credentials.** No customer MFS credentials are ever handled.
- **Cash on Delivery is the only active payment method (ADR 0015).** No online gateway, provider SDK, credential, endpoint, webhook or checkout UI exists, and **none is authorized**. Automated online payment is a future roadmap item: do not build it, do not add a speculative gateway abstraction, and do not reintroduce the retired manual prepaid flow (bKash/Nagad selection, recipient configuration, payment claims or a verification queue).
- **The approved active payment method is Cash on Delivery (D7, narrowed by ADR 0015).** COD has no verification step: the courier collects cash, the owner confirms the order by phone before dispatch, and failed delivery and cash reconciliation are separate states. Do not route a COD order through any prepaid state or queue.
- **The D8 prepaid claim fields are withdrawn with the flow they belonged to (ADR 0015).** No sender number, transaction reference, claimed amount, recipient account or screenshot is requested, collected, stored or displayed. Do not reintroduce them, and do not add an owner screen that configures a receiving account.
- **A guest order can be claimed into an account, once (ADR 0032, 2026-11-09).** The receipt asks a signed-out guest whether to keep the order in an account, and a signed-in customer viewing a guest order gets one button: **Add this order to my account**. Signing in never claims anything by itself - the claim is an explicit POST behind `guardCustomerMutation` (`/api/account/orders/claim`), and it is the only path that writes `order.customer_id` after insert. The database permits exactly one transition, `null -> a customer` (`queenbees_guard_order_immutable_columns`, migration 0019); moving the owner to another account or clearing it is still refused with `23514`, so do not add a transfer, merge or unclaim. The claim writes one `order_event` (`order_claimed`, actor `customer`, `event_key claim:<orderId>`), **no audit row** (D23 - it is customer activity), and no amount, delivery split, discount snapshot or state column changes. A claimed **completed** order does make the account a returning customer for a later delivery quote (ADR 0029) - that is the intended outcome, not a bug. `RECEIPT_PATH_PATTERN` is the one addition to `safeCustomerNext`'s allowlist, bounded to one order number.
- **Guest checkout is an owner switch (D12, ADR 0024).** Off: sign in first, cart preserved. On (Settings -> Other): a name, a phone and an address suffice - no account, so no history and no ban. Absent = off; a guest post is same-origin checked; a customer's order number stays private.
- **Object storage boundary (D3, approved - ADR 0006): Neon Object Storage.** Image **bytes** live in Neon Object Storage (S3-compatible, branches with the database); image **metadata and our own object key** live in PostgreSQL. Never store product image bytes in PostgreSQL - no documented technical constraint justifies it - and never use Vercel's writable temporary filesystem for persistent uploads. The database never stores a provider URL as a product's identity, because Neon's public URLs embed the branch id.
- **Never point a development or preview environment at the production storage branch.** Neon isolates writes per branch, but the credential is lineage-bound rather than environment-bound, so isolation depends on each environment having its own endpoint and credential.
- **Never invent an expiry or release path.** No expiry writer, scheduler or automatic stock release exists, and no reservation is written (ADR 0013). If a future phase adds one, it must be state-guarded and must never touch an order that carries a submitted claim.
- **Refunds are deferred and out of scope for this launch (owner decision, 2026-10-20).** The owner decided to skip refunds completely for now. **Do not build a refund screen, service, route, permission, transition or accounting logic**, and do not add refund work to the roadmap - a future refund feature is a **new owner decision**, not an implementation convenience. **The schema keeps the `refund` table and its four states** (`requested`/`processing`/`completed`/`failed`), unused and written by nothing, like the reservation and claim tables: do not drop them, do not migrate them, and do not touch historical rows. A refund is settled **outside the platform**, so the platform **cannot** state that one happened - no screen, notice or dashboard figure may imply a refund occurred, and no refund amount enters a revenue total. The separation rules below still bind anything that ever touches refund data.
- **Do not invent payment, delivery, expiry or refund policy.** Durations, deadlines, charges and eligibility are owner decisions. **Cash on delivery is the only payment method (ADR 0015)**, the **24-hour unpaid-order expiry is deferred and no expiry writer exists**, cancellation after the window is a support decision before dispatch or a return after it, and refunds are manual and updated only on confirmed real-world action. **Delivery charges are owner-configured since Phase 19 (ADR 0016)**: three areas (Dhaka, Chattogram, Other districts), a required default for Other districts and optional Dhaka/Chattogram overrides, priced server-side and snapshotted on the order. **The actual BDT amounts are still owner inputs**; no price may be guessed, and an unconfigured default refuses checkout rather than charging zero. The storefront states no customer-facing delivery deadline or promise, and historical orders without an area keep their old wording.
- **D11 allocation rule (historical; no longer reachable since ADR 0015). The rule was: the first submitted payment claim gets the product.** Priority is by **claim submission order**, not by order placement and not by verification order. A later claim may **preempt** an earlier order that has **not submitted** a claim. An order that **has** submitted a claim is **never** preempted and **never** released by a timer. **At most one active submitted claim exists per unit** - once a unit carries a claim, no further claim is accepted for it. A losing customer who transferred before submitting must be refunded manually through support.
- **The surviving part of D9 is the COD lifecycle.** The owner approves a COD order before dispatch; cancellation before dispatch is a support decision and after dispatch a return; refunds are manual with separate states; delivery completion, cash collection and cash reconciliation stay separate. **The prepaid halves of D9 and D11 - the verification maximum, the exceptions queue, claim priority and false-claim findings - are retired with the manual flow (ADR 0015)** and exist only as schema rules for tables the application no longer writes. Do not publish or implement a policy the owner has not approved - a guessed policy becomes a published commitment.
- **A customer ban is never inferred from a payment event.** There is no prepaid payment state to misread: the review flag stays **admin-set only**, always carries an audited reason and actor, and an ordinary unpaid or cancelled order never sets it. A rejected COD order is not an accusation and never bans anyone.
- **Never report a refund as completed because it was requested or approved.** `refund_status` (`requested` / `processing` / `completed` / `failed`) is a separate field from `payment_status` and from `order.status`.
- **Never collapse payment status, order status, refund status, inventory reservation state and the customer review flag.** They are five separate, auditable concepts.
- **No automatic cancellation, expiry sweep or stock release exists, and none may be added without an owner decision.** A cancelled COD order is the owner's explicit action, not a timer's.
- **Do not provision infrastructure, create provider accounts, deploy, or change DNS** without explicit owner approval. Approval of a *provider* (ADR 0005) is not approval to provision it: the owner approved Neon and Vercel as choices, not the creation of resources.
- **Cost policy (owner-approved):** keep initial infrastructure costs as close to zero as reasonably possible; **do not upgrade pre-emptively**; justify any upgrade from measured usage, actual plan limits, reliability requirements or business growth. **Recheck current provider pricing and plan terms before implementation and before any upgrade recommendation** - the stated ~$15/mo (Neon) and ~$20/mo (Vercel) figures are the owner's intended future budget, not guaranteed prices.
- Treat persisted cart data as untrusted - both `localStorage` and the `qb_cart` cookie mirror: parse defensively, validate ids against the catalog, clamp numeric values, and never let the mirror decide anything beyond which products a page projects.
- Never render untrusted HTML. Product copy is plain text by design; do not introduce `dangerouslySetInnerHTML` or an unreviewed sanitizer.
- Public image visibility is not a licence. The imported product photography is tagged `rights: 'merchant_source_pending_confirmation'` and is **not** cleared for public launch. Do not relabel it as cleared, and do not add further merchant assets without recorded permission - see `docs/catalog.md`.
- **The interface is English only (Phase 28).** One dictionary (`src/i18n/dictionaries.ts`), one `html lang="en"`, no language toggle and no locale store. Do not reintroduce a second interface language, a toggle, or a stored preference read. `npm run check:i18n` asserts the dictionary is complete, contains no Bengali, every referenced key exists, and no application-owned interface file carries Bengali text. Product and category records keep their `name_bn`/`name_en` columns and Bengali customer text is still rendered - that is data, not interface copy.
- Announcement content: the owner's news line is stored in `store_setting` (`announcement.message`, `announcement.visible`) and edited at **Settings -> Announcement bar**; it is composed on the server and rendered alone. `src/data/announcements.ts` is an **empty typed list** kept as the composition point - a future notice that must never be switched off would be declared there with `locked: true`, and `npm run check:catalog` refuses any locked entry, so adding one is a documented decision rather than a quiet edit. It **scrolls like a ticker**; `prefers-reduced-motion` restores the static line.
- **Delivery pricing has one hierarchy, and a guest never climbs it (ADR 0029).** `quoteOrderDelivery` in `src/lib/delivery.ts` is the only resolver: **repeat delivery -> conditional delivery -> active district override -> configured default -> refusal**, with `repeatDiscountMinor` for the automatic discount. The cart, the checkout preview and `createOrder` all call it, so a shown price and a stored snapshot cannot disagree; never re-derive a charge or a discount in a route, a view or the browser. **Repeat customer means `order.status = 'completed'`**, read inside the order transaction - a pending, cancelled, rejected or unpaid order never counts, and a guest (`customer_id IS NULL`) never qualifies. The conditional and repeat rules are **off by default** and every amount is nullable on purpose: a rule that is on but has no rate for an area **falls through** rather than charging a guessed number. The repeat delivery rate has **two** fields (Chattogram; Dhaka and every other district) - do not invent a third. The automatic discount is added to any promotion code and the pair is capped at the goods subtotal; both are snapshotted in `order.discount_minor` / `order.shipping_minor`, and the database still checks `total = subtotal - discount + shipping`.
- **Payment instructions on checkout are owner copy, not a payment method (ADR 0029).** `payment.instructions`, `payment.bkash_number`, `payment.bkash_visible`, `payment.send_money_note` and `payment.advance_threshold_minor` live in `store_setting`, are edited at **Settings -> Other settings -> Checkout instructions** (moved there on 2026-11-09; `settings.write`, audited `settings.payment_instructions_updated`), refuse `<`/`>`, and render as plain paragraphs with the number labelled **bKash Advance**, bold and with a copy button. `payment.bkash_visible` is the owner's explicit show/hide switch for that number block - blank-number-means-no-block survives, but the switch is what turns the block off without deleting the number. The Bangla defaults are **owner data** in `src/data/payment-instructions.ts` (on `check:i18n`'s data allowlist); do not move them into the English dictionary. **Cash on Delivery is still the only method an order records** - do not add a payment selection, a claim, a screenshot upload or a verification queue without a new owner decision that supersedes ADR 0015, and never let checkout copy promise something the order cannot record.
- **Customer email is for account security only, and it never gates access (ADR 0030).** Resend sends exactly four messages: a password-recovery link, a password-changed notice, a new-address confirmation, and an address-changed notice to the previous address. **Registration and sign-in have no verification step and send no mail** - do not add one, and do not add a registration confirmation. Tokens are 256 bits from `createOpaqueToken()`, stored only as a SHA-256 digest, single-use (a guarded `UPDATE ... WHERE used_at IS NULL`), and expire (an hour for recovery, a day for an address change); a dead token answers exactly like an unknown one. **A recovery request answers identically for every outcome** - registered, unknown, suspended, malformed, throttled, provider down - and is throttled by address and source; never make that response "helpful". `RESEND_API_KEY`, `EMAIL_FROM` and `APP_BASE_URL` come from the environment only (the key is never in a row, a log, a redirect or a bundle; `APP_BASE_URL` is required in production or no link is sent), and `RESEND_API_BASE_URL` is a development-only test seam. A password change revokes every customer session and mints one replacement for the current browser; a confirmed address change revokes every session and mails the previous address. **The account's address never moves when it is typed** - only when the mailed confirmation button is pressed. Do not touch admin authentication: no verification, no recovery mail, no new step.
- **SteadFast booking is one call on COD approval, and it never changes an order state (ADR 0028).** Approving a COD order in the confirmation queue books the consignment (`POST /create_order`) **after** the approval transaction commits, in its own transaction, so a courier outage cannot undo the owner's phone decision: the order stays `cod_approved` / `confirmed`, `order.steadfast_booking_failed` is written separately, and **Send to SteadFast** on the order screen is the retry. `steadfast_consignment` holds **one row per order** (unique `order_id`, unique `invoice` = the order number, unique courier consignment id, plus a transaction-scoped advisory lock), so a second send answers "already booked" instead of creating a second parcel. **A booking, a failure and a status refresh touch no order state** - SteadFast's `delivered` is stored on the consignment with `status_checked_at`, never applied to `order.status`, `order.cod_state`, payment, refund or stock; cash receipt stays the owner's explicit act. The amount to collect is the frozen `total_minor` in BDT and is never re-derived; the address is composed from the stored line plus area/city/postcode; a phone that is not an 11-digit Bangladeshi mobile is refused before the call. **The courier's `Api-Key`/`Secret-Key` live in `store_setting`** (`steadfast.api_key`, `steadfast.secret_key`, `steadfast.enabled`), entered at **Settings -> Integrations -> SteadFast**, returned to the browser only as `••••` plus the last four characters, and never logged, redirected or audit-recorded as values - the deliberate exception to the environment-only rule, because an owner rotates this pair from the courier's portal. Booking is **off by default** and cannot be switched on without both keys. Do not add a statement import, cash reconciliation, label/pickup/bulk/fraud endpoints, a second courier, or an automatic order transition from a courier event without a new owner decision.
- **Telegram alerts are advisory**: env-only token, `telegram_recipient` chat ids, failures swallowed in `after()` so they never fail an order (ADR 0022). The message is a plain-text receipt of what the order recorded (lines, totals, area, contact, note), never a promise or a command channel.
