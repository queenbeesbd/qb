# Project audit - 2026-10-30

Repository: QueenBee's storefront + admin (single-store, owner-operated shop, ADR 0008).
Commit at audit time: `087729b` ("Phase 44: the storefront survives the real catalog") plus an
uncommitted working tree that contains the Phase 45 / 45b / 46 work.
Environment: local only. **Nothing is deployed and no QueenBee's-bound cloud resource exists.**

Requested outcome: audit the project, write a detailed implementation plan from scratch, and add a
changelog. **No application code was changed by this audit.**

---

## 1. What this audit is, and is not

This is an evidence-first review of the repository as it stands: source, schema, scripts, tests and the
documented decisions, plus the checks that can be run without a database cluster, a served build, or an
owner session.

It is **not** a penetration test, a browser/device/accessibility pass, or a production readiness
sign-off. Section 9 states exactly what was not verified.

## 3. What the project actually is (verified facts)

- **One store, one owner.** No `store_id`/`tenant_id`, no marketplace surface (ADR 0008). Admin is
  owner-only, every owner has full access (ADR 0009).
- **Cash on Delivery is the only payment method** (ADR 0015). The manual prepaid flow was removed; the
  `payment_claim` / `payment_recipient` tables remain implemented and unwritten.
- **The catalog is real.** 1,605 products (1,477 published + 128 archived), 245 brands, 15 categories,
  1,919 image derivatives, 528 customers and 559 orders were imported from the owner's previous store
  (`scripts/import-zatiq.ts`, `docs/migrations/zatiq-easy-import.md`).
- **Availability is a state, not a quantity** (ADR 0010/0013). It is the only ordering gate; no
  reservation, deduction or movement is written; overselling is accepted.
- **Orders are atomic and server-authoritative**; prices come from `product_variant`, totals from the
  server, idempotency key claimed inside the transaction, promo discount snapshotted on the order.
- **Customer auth is first-party** (ADR 0012): scrypt, hashed session tokens, idle + absolute expiry,
  account- and source-keyed throttling, customer-scoped CSRF, separate cookie and tables from the owner.
- **Guest checkout is an owner switch** (ADR 0024), default off; when on, an order is written with
  `customer_id = null` and an `order_placed` event with `actor_type = 'guest'`.
- **Promo codes are a rule plus a derived use count** (ADR 0021): one code per order, no stacking, usage
  is `count(*)`, the last use is protected by locking the code row inside the order transaction.
- **46 tables**, validated by `tests/unit/schema-integrity.test.ts`, migrated by Drizzle under
  `drizzle/`, append-only tables protected by revoked grants *and* triggers.

## 4. Verified strengths (the plan must preserve these)

1. **The refusal is the design.** Percentages, discounts, availability, ownership and totals are all
   resolved server-side; the browser sends ids and quantities only.
2. **The seams are real.** `src/server/catalog/storefront.ts` is the only catalog accessor the views
   know; the cart stores ids, not product records; `qb_cart` holds ids only and can only select which
   products a page mentions.
3. **Documented decisions match the code.** Spot checks of ADR 0013 (no reservation write), ADR 0015 (no
   prepaid path), ADR 0018 (cost immutability), ADR 0021 (derived usage, snapshotted discount) and
   ADR 0023 (reversible ban, reason required) all matched their implementations.
4. **Security hygiene is above the norm for this stage:** origin check that prefers `Host` and ignores
   forwarded headers unless explicitly trusted, CSRF derived from the session token, safeEqual compares,
   open-redirect allowlists by exact shape, denials written in their own transaction, no secret in the
   client bundle, `npm run check:secrets` in CI.
5. **Honesty rules are actually enforced:** no invented ratings, stock counts, dates or delivery
   promises; out-of-stock products cannot be ordered and the PDP removes the control instead of letting
   it fail; the comparison price is struck through only when the saving is real.
6. **Unit tests are meaningful**, not decorative: schema/migration integrity, cart-cookie parsing,
   promo evaluation, delivery quoting, request guards, password parsing, storefront fixture guards.

## 5. Findings

Severity: **P1** = blocks or corrupts a launch-surface behaviour; **P2** = real defect or measurable
cost with a workaround; **P3** = polish. "Defect" means the running build does the wrong thing today;
"gap" means a capability is absent by decision or omission; "risk" means a plausible failure that has
not happened yet.

### 5.1 Storefront

**AUD-01 (P1, defect) - Guest checkout cannot use a promotion code.**
The promo preview route is gated on a customer session
(`src/app/api/checkout/promo/route.ts` calls `guardCustomerMutation`), but `CheckoutForm` renders the
promo field unconditionally and guest ordering is an approved switch (ADR 0024). A guest types a valid
code, the route answers `unauthenticated`, and the form maps that unknown reason to its generic failure
(`checkout.promo.failed`). The order route *would* accept a guest promo code, but the hidden field can
only be filled after a successful preview, so a published promotion is silently unusable for exactly the
customers the owner enabled guest ordering for.
Phase 47.

**AUD-02 (P1, defect) - Checkout has no explicit invalid-field summary.**
`src/features/checkout/CheckoutForm.tsx` relies on native constraint validation only: no `noValidate`,
no `role="alert"` summary, no `aria-invalid`, no focus management. Lines 188-240 hold `required`,
`minLength`, `maxLength` and a `pattern="01[3-9][0-9]{8}"`. On a phone this is a transient browser bubble
with browser-authored wording, in a long form, for the highest-stakes action in the shop. The project
already solved this for its editors and named the pattern (`_ui/ProductForm.tsx:144-148`,
`PromoCodeForm.tsx:197`): `noValidate` plus a named problem list plus focus on the first invalid field.
Phase 47.

**AUD-03 (P2, defect) - "Clear cart" destroys the basket with one tap and no undo.**
`src/features/cart/CartView.tsx:233` calls `cart.clear` directly. The admin surface requires a reasoned
confirmation for far less destructive actions; the storefront offers none, and a mis-tap loses every
line. Phase 48.

**AUD-04 (P2, defect) - The guest receipt lives in the account tree and breaks when a dead session
cookie is present.**
A guest order is redirected to `/account/orders/<number>?placed=1`. The page decides "anonymous" by
**cookie presence**, not by session validity
(`src/app/(storefront)/account/orders/[orderNumber]/page.tsx`), so a guest whose browser still holds an
expired cookie takes the signed-in branch, is sent to sign in, and cannot see the order they just
placed. The route also reads as an account-owned resource and the page header uses `orders.title`
("My orders") for a guest. Phase 49.

**AUD-05 (P2, gap) - The product page shows only the first photograph.**
`ProductDetailView.tsx:54` uses `product.images[0]`. The catalog holds **1,919** image derivatives for
1,605 products, and the admin media panel already stores and reorders multiple images per product
(`ProductMediaPanel.tsx`). Owner curation is invisible to customers, and the PDP is weaker than the data
allows. No schema change is needed. Phase 50.

**AUD-06 (P1 for launch, gap) - No contact, delivery, returns or privacy surface - while the copy tells
customers to contact the store.**
`Footer.tsx` lists only shop, cart, checkout and account. `account.recoveryContactNote` tells a customer
locked out of their account to contact the shop; there is no phone number, address, hours or support
route anywhere on the storefront. For a COD shop this is both a trust problem and an operational dead
end: a customer who needs to change an address before dispatch has nowhere to go. The content is an
owner decision (the shop's real phone, hours, and wording for delivery/returns/cancellation), not
something engineering may invent. Phase 51.

**AUD-07 (P3, gap) - Between 1024px and 1199px the search control is a link, not a field.**
`Header.tsx` renders `compactSearch` as a link to `/products`; a shopper who taps the magnifier gets
the listing and must find the field again. Phase 57 (optional).

**AUD-08 (P1 for launch, gap) - The store cannot be indexed.**
`src/app/layout.tsx:29` sets `robots: { index: false, follow: false }` globally, and there is no
`robots.txt`, sitemap, canonical URL, OpenGraph image or structured data. That is correct *today*
(noindex until launch) and wrong the moment the owner launches. Per-product `generateMetadata` exists,
so the missing pieces are the policy flip plus the inventory surfaces. Phase 57.

**AUD-09 (P2, owner decision) - A guest who loses the confirmation URL can never see the order again.**
The order number is the only handle and it is only reachable from the URL. A "find my order" form
(number + phone) is a product decision with a real enumeration trade-off, so it is proposed as a
decision, not smuggled in as a fix. Phase 49.

### 5.2 Admin

**AUD-10 (P2, defect) - The image inventory re-lists 15,568 files on every call.**
`src/server/catalog/assets.ts` derives the allowlist with `readdir` inside `listAssetKeys()`, which
`isKnownAsset()` calls, and `readAsset()` calls again before reading 8 variant files per key. Every
render of the product media panel pays a full directory listing; every association pays several. The
work is bounded and correct, but it grows with the asset tree and has no cache. Phase 54.

**AUD-11 (P2, gap) - No printable dispatch paperwork.**
A COD dispatch is a physical hand-off: the courier needs the address, phone, order number and the cash
amount. No route emits a packing slip, address sheet or printable order view (no `window.print` path
exists in the admin). The owner can read the detail page on a phone, which is not the same thing.
Phase 52.

**AUD-12 (P3, gap) - No bulk catalog operation or export.**
With 1,605 products the catalog list offers search, filter, pagination and a per-row availability
switch, but no bulk availability change and no export. This is operational polish, not launch-critical.
Phase 54 (optional slice).

**AUD-13 (P1 for launch, gap by decision) - There is no image upload.**
ADR 0006 approved Neon Object Storage; it is not provisioned, and imagery is association-only from the
local tree. The owner cannot add a product with new photography, which is a launch blocker for a shop
that keeps selling new stock. Provisioning needs its own explicit authorization. Phase 53.

### 5.3 Performance and delivery

**AUD-14 (P2, risk) - Every route is dynamic; there is no cache anywhere.**
The storefront layout sets `export const dynamic = 'force-dynamic'`, and the build output is `ƒ`
(dynamic) for **every** route including `/products` and `/categories/[slug]`. Each request re-reads the
catalog (homepage selection, sorts, filters), and there is no data cache, no tag invalidation and no
`revalidate`. On a serverless host with a Neon free-tier branch this is cold-start latency plus
connection cost on the shop's busiest pages. Phase 54.

**AUD-15 (P1 for launch, gap) - Image bytes live in `public/catalog`: 666 MB, ~15,568 files, gitignored.**
The import notes already state the consequence: the directory must be shipped with the app or the images
are broken. A deployment cannot carry it sensibly, and the build itself now warns that the asset glob
matches 15,568 files. The image *identity* is already a key, not a URL, so the migration is a delivery
change rather than a schema change. Phase 53.

**AUD-16 (P1, dependency risk) - The build stops on Next's own security advisory.**
`npm run build` aborts once with `SecurityFatalError: Your version of Next.js is affected by a known
security vulnerability` (Next 16.4.0). The project documents this as framework behaviour, and a retry
proceeds, but the advisory itself is a dependency fact that should be resolved before launch. Phase 56.

**AUD-17 (P2, gap) - No health endpoint, no monitoring, no structured log.**
The only outbound signal is the Telegram order alert (ADR 0022, advisory); the only log line is
`console.error` in the denial logger. Nothing answers "is the database reachable right now" or
"did the site 500 for the last hour". Phase 60.

### 5.4 Abuse and security

**AUD-18 (P1, risk) - Guest order creation is unthrottled.**
`POST /api/checkout/order` has no rate limit: the auth flows are throttled (account + source keyed), the
order route is not. With guest ordering enabled, an unauthenticated client can create unlimited orders -
rows, events, delivery lookups and Telegram alerts to the owner. This is the natural consequence of
ADR 0024 that was not closed. Phase 55.

**AUD-19 (P2, gap, already recorded) - No Content-Security-Policy.**
`next.config.ts` sets frame, sniffing, referrer and permissions headers and explicitly documents why a
CSP is absent. The storefront renders no untrusted HTML, so this is hardening rather than an open hole,
but it is a launch-grade header and `docs/security.md` lists it as open. Phase 56.

**AUD-20 (known, owner action) - A gitignored `.env` holds a plaintext credential for the withdrawn vendor
dashboard.** Read by no code, never committed; rotation and removal are the owner's actions. Not touched
by this audit and it must not be read into output. Phase 60 checklist item.

**AUD-21 (P1, cross-cutting) - Credential recovery depends on a contact channel that is not published.**
AUD-06 and the recovery flow compound: the customer is told to contact the shop, and the shop publishes
no way to be contacted. Phase 51 closes the loop; it is content, not new policy.

## 6. Honesty-rule conformance (spot check against AGENTS.md)

**Holds:** no invented stock, dates, ratings, sales counts or testimonials; no "only N left" style
urgency; the comparison price is struck through only when the saving is real; an out-of-stock product
cannot be ordered and the storefront states the reason rather than showing a failing button; COD has no
verification step and no screen implies cash was collected before `cod_collected` is recorded; no
traffic or page-view figure exists.

**Would break at launch if shipped as-is:** `noindex` is still global (correct now, wrong at launch);
the photography is uncleared; the shop publishes no way to contact it while its own copy says to.

## 8. Summary

The commerce core is in better shape than the surrounding product surface. Orders, pricing, promo
evaluation, sessions, authorization and the append-only guarantees are designed and implemented with
unusual care, and the documentation records the limits instead of hiding them. The defects that remain
are concentrated where the project recently moved fastest: **guest checkout** (promo preview, receipt
route, abuse control), **storefront presentation** (gallery, support surfaces, discoverability), and
**delivery** (local image bytes, no cache, no monitoring). None of them require a schema change, a new
dependency, or a new business policy - but several require an owner decision or an explicit
authorization before they can be implemented.

See `docs/implementation-plan-2026-10-30.md` for the phased plan and `CHANGELOG.md` for the record.

**New finding found while verifying, and fixed in the same change:**

**AUD-32 (P1, defect, fixed) - A repeated guest submission returned a conflict instead of its order.**
`loadCreatedOrder` in `src/server/orders/create.ts` matched `order.customer_id = 0` as a guest sentinel,
while a guest order is written with `customer_id is null`. A guest double-submitting the same form was
therefore told "that submission was already processed" and redirected to checkout, with no order list to
open - a dead end after an order that had, in fact, been created. The match is now
`customer_id is not distinct from $1`, with a database test for the guest replay and for a customer who
tries to claim a guest's key. Retrospective note: this was present since guest checkout shipped and the
existing idempotency tests only covered signed-in customers, which is exactly the coverage gap Phase 61 is
for.
